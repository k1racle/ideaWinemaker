# План внедрения админ-панели и SQLite

## 1. Цель

Добавить в существующий Nuxt-проект закрытую админ-панель, через которую авторизованный администратор сможет:

- добавлять виноделов;
- добавлять вина и обязательно связывать каждое вино с существующим виноделом;
- скрывать и повторно показывать виноделов и вина без физического удаления;
- скрывать виноделов или вина;
- при скрытии винодела - скрывается его вино
- заполнять все поля, которые сейчас описаны в `shared/mock/winemakers.ts` и `shared/mock/wines.ts`;
- после сохранения сразу видеть новые сущности на публичных страницах сайта.

Существующие и новые данные должны храниться в SQLite. TypeScript-массивы перестанут быть источником данных во время работы приложения.

## 2. Что есть в проекте сейчас

- Nuxt 4.5.1 и Vue 3.
- Три винодела находятся в `shared/mock/winemakers.ts`.
- Шесть вин находятся в `shared/mock/wines.ts`.
- Публичные страницы и компоненты импортируют массивы напрямую и работают синхронно.
- Отдельных каталогов `server/`, API, базы данных и механизма авторизации пока нет.
- Связь сейчас продублирована в двух направлениях:
  - у винодела — `meta.wineSlugs`;
  - у вина — `meta.winemakerSlug`, `winemakerName`, `winemakerCode`.

Главная проблема текущей связи — эти значения можно изменить независимо друг от друга и получить противоречивые данные.

## 3. Предлагаемые технические решения

### 3.1. Сервер и база данных

- Использовать встроенный серверный слой Nuxt/Nitro (`server/api`, `server/utils`, `server/middleware`).
- Использовать SQLite как единственный runtime-источник виноделов и вин.
- Для типизированной схемы и управляемых миграций использовать Drizzle ORM и Drizzle Kit.
- Для локального файла SQLite использовать драйвер `better-sqlite3`.
- Путь к базе задавать серверной переменной `DATABASE_PATH`.
- Локальное значение по умолчанию: `.data/ideawinemaker.sqlite` внутри каталога `nuxt`.
- Сам файл БД, WAL-файлы и резервные копии не добавлять в Git.
- При подключении включать `PRAGMA foreign_keys = ON`, `journal_mode = WAL` и разумный `busy_timeout`.

Важно: приложение потребуется запускать через `nuxt build` как Node/SSR-сервер. Статическая сборка `nuxt generate` не может обслуживать авторизацию, API и изменяемую локальную SQLite.

### 3.2. Авторизация

Для первой версии достаточно одного администратора без публичной регистрации:

- логин задаётся в `ADMIN_LOGIN`;
- в `ADMIN_PASSWORD_HASH` хранится только хеш пароля;
- сессия хранится в защищённой `httpOnly` cookie через `nuxt-auth-utils`;
- ключ шифрования сессии находится в `NUXT_SESSION_PASSWORD`;
- секреты присутствуют только в `.env`/настройках хостинга и не попадают в клиентский bundle или Git.

Клиентский middleware будет закрывать страницы `/admin/**`, но окончательная проверка прав обязательно выполняется отдельно в каждом серверном admin API. Для логина нужно предусмотреть ограничение частоты попыток и одинаковый текст ошибки для неверного логина и пароля.

Если позже понадобятся несколько администраторов и управление их доступом, можно добавить таблицу `admin_users`; для заявленного MVP она не нужна.

### 3.3. Сильная связь винодела и вина

Связь в базе:

```text
winemakers (1) ──────── (N) wines
                 wines.winemaker_id NOT NULL
```

- `wines.winemaker_id` — обязательный внешний ключ на `winemakers.id`.
- Вино нельзя сохранить без существующего винодела.
- Для внешнего ключа используется `ON DELETE RESTRICT`: винодела с привязанными винами нельзя случайно удалить.
- Создание вина и его вложенных данных выполняется одной транзакцией.
- В первой версии удаление вообще не входит в интерфейс; правило `RESTRICT` заранее защищает целостность данных.

В БД не нужно отдельно хранить `winemakerSlug`, `winemakerName`, `winemakerCode` внутри вина и `wineSlugs` внутри винодела. Эти поля будут формироваться серверным mapper-слоем из одной реальной связи. В результате публичные интерфейсы `Wine` и `Winemaker` сохранят текущую форму, но дубли данных исчезнут.

## 4. Предлагаемая схема SQLite

### `winemakers`

Поля:

- `id` — integer primary key;
- `slug` — обязательное уникальное текстовое поле;
- `title`;
- `excerpt`;
- `content`;
- `image`;
- `quote`;
- `initials` — текущее `meta.initials`;
- `location` — текущее `meta.location`;
- `about_brand` — текущее `meta.aboutBrand`;
- `created_at`, `updated_at`.
- `is_visible` — флаг показа на публичном сайте, по умолчанию `true`.

### `winemaker_biography`

Хранит массив `biography` без потери порядка:

- `id`;
- `winemaker_id` — внешний ключ с `ON DELETE CASCADE`;
- `position`;
- `text`.

Уникальная пара `(winemaker_id, position)` не позволит двум абзацам занять одну позицию.

### `wines`

Поля:

- `id` — integer primary key;
- `winemaker_id` — обязательный внешний ключ на `winemakers.id`, `ON DELETE RESTRICT`;
- `slug` — обязательное уникальное текстовое поле;
- `title`;
- `excerpt`;
- `content`;
- `image`;
- `author_quote`;
- поля из `WineMeta`: `wine_type`, `variety`, `method`, `method_code`, `year`, `alcohol`, `volume`, `terroir_slug`, `terroir_name`, `terroir_code`, `batch`, `bottle_number`, `serving_temperature`, `color`, `aroma`, `taste`, `pairing`;
- `created_at`, `updated_at`.
- `is_visible` — собственный флаг показа вина, по умолчанию `true`.

`year`, алкоголь, объём, номер бутылки и температура пока остаются текстовыми полями, чтобы без потерь сохранить текущий формат данных (`2025`, `12,0–14,0%`, `0,75 л.`, `001 / 600`, `7–9°С`).

### `wine_gallery`

Хранит необязательный массив `gallery`:

- `id`;
- `wine_id` — внешний ключ с `ON DELETE CASCADE`;
- `position`;
- `image`.

### `wine_terroir_paragraphs`

Хранит массив абзацев `terroir`:

- `id`;
- `wine_id` — внешний ключ с `ON DELETE CASCADE`;
- `position`;
- `text`.

### `wine_detail_groups` и `wine_detail_items`

Сохраняют текущую вложенную структуру `details: { title, items[] }[]` и порядок групп/строк:

- группа: `id`, `wine_id`, `position`, `title`;
- строка: `id`, `group_id`, `position`, `text`.

Такой вариант немного объёмнее хранения JSON, зато даёт явные ограничения, предсказуемое редактирование и сохранение порядка. Все дочерние записи удаляются каскадно только вместе со своим вином.

## 5. Совместимость с текущими TypeScript-полями

Интерфейсы нужно вынести из mock-файлов, например в `shared/types/content.ts`, чтобы ими могли пользоваться клиент, API и mapper-слой.

Сервер возвращает объекты в прежнем формате:

- `Winemaker.biography` собирается из `winemaker_biography` по `position`;
- `Winemaker.meta.initials`, `location`, `aboutBrand` берутся из колонок винодела;
- `Winemaker.meta.wineSlugs` вычисляется из связанных записей `wines`;
- `Wine.gallery`, `terroir` и `details` собираются из дочерних таблиц по `position`;
- `Wine.meta.winemakerSlug`, `winemakerName`, `winemakerCode` берутся через join с `winemakers`;
- остальные поля `Wine.meta` берутся из колонок `wines`.

Это позволит сначала заменить источник данных, почти не меняя шаблоны карточек и детальных страниц.

## 6. API

### Публичное чтение

- `GET /api/winemakers` — список виноделов;
- `GET /api/winemakers/:slug` — один винодел вместе с `wineSlugs`;
- `GET /api/wines` — список вин, при необходимости с фильтрами `year`, `terroir`, `winemaker`, `method`;
- `GET /api/wines/:slug` — одно вино со всеми вложенными данными и информацией о виноделе.

### Авторизация

- `POST /api/admin/login`;
- выход и получение текущей сессии — средствами `nuxt-auth-utils`.

### Закрытая запись

- `POST /api/admin/winemakers` — создать винодела и его биографию одной транзакцией;
- `POST /api/admin/wines` — создать вино, привязку к виноделу, галерею, терруар и группы деталей одной транзакцией;
- `PATCH /api/admin/winemakers/:id/visibility` — скрыть или показать винодела;
- `PATCH /api/admin/wines/:id/visibility` — скрыть или показать вино;
- `POST /api/admin/media` — загрузить изображение, если согласуем загрузку файлов через форму.

Все входящие данные проверяются на сервере общей схемой валидации, например Zod. Нужно проверять обязательные поля, длину строк, формат и уникальность slug, существование `winemaker_id`, структуру массивов и допустимость путей/файлов. Ожидаемые ответы: `400/422` для неверных данных, `401` без сессии, `409` для занятого slug.

## 7. Изображения

SQLite должна хранить путь и метаданные, но не бинарное содержимое изображений.

Рекомендуемый вариант:

- существующие файлы продолжают читаться из `public/uploads`;
- новые изображения загружаются в отдельный постоянный каталог, заданный через `MEDIA_ROOT`;
- сервер отдаёт их по стабильному URL `/media/...`;
- имя файла генерируется сервером и не зависит от исходного имени;
- разрешаются только согласованные MIME-типы, например JPEG, PNG и WebP;
- задаётся предел размера файла;
- каталог с новыми файлами резервируется вместе с SQLite.

Если на первой итерации загрузка файлов не нужна, поле `image` и элементы `gallery` можно временно вводить как готовые URL/пути. Это уменьшит объём MVP, но потребует загружать файлы отдельно.

## 8. Страницы админ-панели

### `/admin/login`

- логин;
- пароль;
- понятная общая ошибка авторизации;
- переход в `/admin` после успешного входа.

### `/admin`

- информация о текущей сессии;
- количество виноделов и вин;
- ссылки «Добавить винодела» и «Добавить вино»;
- выход из системы.

### `/admin/winemakers/new`

- все скалярные поля текущего `Winemaker`;
- динамический список абзацев `biography` с добавлением, удалением и изменением порядка;
- предварительный просмотр изображения;
- ручной slug с возможностью автоматически получить начальное значение из заголовка;
- показ серверных ошибок рядом с соответствующими полями.

`meta.wineSlugs` в форму не выводится: список формируется автоматически из реальных связей.

### `/admin/wines/new`

- обязательный выбор винодела из списка БД;
- все скалярные поля текущего `Wine` и `WineMeta`;
- динамические списки `gallery` и абзацев `terroir`;
- динамические группы `details`, внутри каждой — упорядоченный список строк;
- предварительный просмотр основного изображения и галереи;
- защита от повторной отправки формы;
- переход на созданную публичную страницу после успешного сохранения.

Поля `winemakerSlug`, `winemakerName`, `winemakerCode` отдельно не редактируются: они определяются выбранным виноделом.

Редактирование и удаление существующих записей не входят в заявленный MVP. Вместо удаления доступны переключатели видимости. Скрытый винодел маскирует на публичном сайте связанные вина, но не меняет их собственные флаги.

## 9. Перенос существующих данных

1. Создать схему Drizzle и первую SQL-миграцию.
2. Сделать одноразовый идемпотентный импорт текущих массивов в пустую SQLite.
3. Сначала импортировать виноделов с сохранением текущих `id` и `slug`.
4. Импортировать биографии в исходном порядке.
5. Импортировать вина, находя `winemaker_id` по `wine.meta.winemakerSlug`.
6. Импортировать галерею, терруар и детали с явным `position`.
7. В одной проверке убедиться, что:
   - импортировано 3 винодела и 6 вин;
   - все текущие slug уникальны;
   - у каждого вина существует винодел;
   - списки `wineSlugs` совпадают с фактическими связями;
   - ни одно поле и ни один элемент массивов не потерян.
8. Повторный запуск импорта не должен создавать дубликаты.
9. До переключения production сделать резервную копию исходных TS-файлов и созданной БД.
10. После проверки всех окружений убрать импорты mock-массивов из runtime-кода. Сами mock-файлы можно удалить после завершения переноса; временный import-скрипт хранить отдельно от приложения только столько, сколько требуется для миграции окружений.

## 10. Перевод публичного сайта на API

Нужно заменить прямые импорты mock-массивов во всех найденных местах:

- главная страница;
- `/about`;

- `/wine/[slug]`;
- `/vinodely`;
- `/vinodely/[slug]`;
- `/search`;
- `WineCodeFilter`;
- типовые импорты в `WineCard` и `WinemakerCard`.

План замены:

2. Реализовать repository/query-слой на сервере, чтобы SQL не дублировался между endpoints.
3. Добавить mapper из нормализованных строк БД в текущие `Wine` и `Winemaker`.
4. Перевести страницы на `useFetch`/`useAsyncData`, сохранив серверный рендеринг для SEO.
5. Фильтры строить по загруженным данным или передавать как query в `/api/wines`.
6. Сохранить текущие URL, slug, 404-ответы, заголовки и meta description.
7. Убрать все runtime-импорты `shared/mock/wines` и `shared/mock/winemakers`.

## 11. Безопасность и надёжность

- Проверять сессию на сервере для каждого изменяющего endpoint.
- Не полагаться только на клиентский route middleware.
- Пароль хранить только в виде стойкого хеша; секрет сессии — не короче 32 символов.
- В production включить HTTPS и `secure` для cookie; использовать `httpOnly` и `sameSite`.
- Для изменяющих запросов проверять origin и не разрешать произвольный CORS.
- Пользовательский текст по умолчанию отображать как текст, а не через необработанный `v-html`.
- Ограничить размер тела запроса, массивов и загружаемых файлов.
- Записывать серверные ошибки без паролей, cookie и других секретов.
- Выполнять регулярный корректный backup SQLite и каталога медиа с проверкой восстановления.

## 13. Минимальный набор проверок

### Автоматические

- mapper полностью восстанавливает текущие структуры `Wine` и `Winemaker`;
- seed создаёт ровно 3 винодела и 6 вин и безопасно запускается повторно;
- нельзя создать вино без винодела или с несуществующим `winemaker_id`;
- нельзя создать второй объект с тем же slug;
- запросы записи без сессии возвращают `401`;
- успешное создание сохраняет вложенные массивы и их порядок;
- при ошибке внутри транзакции не остаётся частично созданного вина/винодела.

### Ручные

- вход, обновление страницы админки и выход;
- добавление винодела со всеми абзацами биографии;
- добавление вина со всеми группами `details`;
- корректная карточка и детальная страница нового объекта;
- новое вино появляется на странице выбранного винодела;
- фильтры вина учитывают новую запись;
- мобильное отображение длинных форм;
- сохранение данных после перезапуска сервера.

## 14. Критерии готовности MVP

- Неавторизованный пользователь не может открыть админку или выполнить запись через API.
- Администратор может войти, выйти, добавить винодела и добавить связанное с ним вино.
- Все текущие поля и порядок вложенных массивов сохраняются.
- Вино нельзя сохранить без валидного винодела.
- Публичный сайт получает виноделов и вина только из SQLite.
- Все 3 текущих винодела и 6 текущих вин перенесены без визуальных и содержательных потерь.
- Новые данные видны на публичных страницах и остаются после перезапуска.
- SQLite и новые изображения находятся на постоянном диске и резервируются.
- Секреты, файл БД и резервные копии не попадают в Git.
- Production build, typecheck и согласованный набор тестов проходят успешно.

## 15. Согласованные решения

1. На production будет постоянный writable-диск.
2. Для первой версии достаточно одного администратора из переменных окружения.
3. В первой версии в изображениях указывается существующий путь/URL, без загрузки бинарных файлов.
4. Первая версия добавляет записи, но не редактирует их поля.
5. Физического удаления нет. Вместо него винодела или вино можно скрыть и повторно показать.
